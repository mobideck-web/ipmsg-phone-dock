# Critical review and update history

## v0.5.0

- Received messages now use a contrasting outlined rounded bubble, matching outgoing messages' grouping. Body text has a 24sp line height; visible web links open normally.
- New outgoing peers require per-IP/user approval. Discovery remains automatic. Removed peers lose approval. This is a consent boundary, not cryptographic device authentication; existing TOFU key verification remains necessary.
- Default accepted downloads use pending MediaStore rows in Download/IPMsg, published after all advertised bytes arrive. The selected SAF folder retains its write grant, and failed/cancelled downloads are deleted. Simultaneous duplicate acceptance disposes of unused destinations. Filename collisions preserve separate files.
- Live camera is an explicitly approved foreground Camera2 activity, not exported. A separate 192-bit random token, exact peer IP and ten-minute deadline control the local browser endpoint. It closes on pause, lock, destruction or expiry, and rejects recording requests from other origins. Only bounded HTTP headers/client queues are processed. No cloud, remote activation, microphone or whole-storage access was introduced.
- Browser recording requests only show an owner dialog. Record creates a pending silent MP4; successful stop publishes it, and a separate action shares it. Owner or viewer can stop an approved recording. Recording errors discard incomplete media; forced process termination can leave pending MediaStore rows for system expiry.
- Live HTTP is unencrypted; this is explicitly stated before starting and sending a link. This implementation is suitable only for a trusted LAN. App permission cannot prevent independent screen capture by an authorized viewer. A signed IPMsg link message does not encrypt the HTTP stream. No security certification is claimed.
- Camera2 size selection intersects supported preview and recorder sizes up to 720p. Unsupported combined sessions fail closed, preserving normal photo/video capture. Android 10 API compatibility was checked by lint. Declaring CAMERA also affects external capture intents, so those actions now request permission before launch.

## v0.4.0

- Renamed the launcher to IPMsg while preserving the application ID and upgrade signing identity. Removed repeated encryption banners and verbose onboarding text from the main screens; kept security details and meaningful sharing warnings.
- Database v4 retains message packet numbers and file records/URI links, with migration from v1/v2/v3. Restored unfinished offers become Expired, because network offers remain session-scoped. Saved file cards persist in their original chats. NOLOG attachment metadata remains volatile. History clearing revokes active offers before deleting message/file links; external saved files remain.
- Added in-app banners and a separate high-importance notification channel rather than attempting to raise the existing channel's user-controlled importance. Message previews are off by default and lock-screen visibility is private. Android retains final control over pop-ups and notification permission.
- Visual checks caught action banners defaulting to indefinite duration. They now expire, include a dismiss action and replace older banners rather than building a queue. Widget state is refreshed when the app resumes after process recreation.
- A runtime switch test caught preferences saving correctly while Compose skipped their visual update. Each switch now observes the state revision directly, with a regression test that toggles in both directions and checks the stored value.
- Added a Home-screen widget with explicit user-driven Connect/Stop/Open actions. No boot receiver or automatic camera/storage exposure was added.
- Camera capture uses Android's photo/video contracts and MediaStore camera targets; successful captures are finalized and cancelled/failed launches cleaned up. No camera/microphone permission is needed because capture is delegated to the system camera application. Storage browsing uses Android's picker; it does not grant full-device or remote storage access.
- Full capture validation found that a MediaStore target marked pending cannot be written by a different camera package despite its URI grant. Camera targets therefore use ordinary local media rows, with cancellation cleanup; sharing over IPMsg still requires confirmation. This avoids an external camera owner-check failure without copying large recordings or requesting broad storage access.
- Device removal persists an IP block and cancels its active offers. A restore action is available. Secure-only messages reject incoming/outgoing plaintext; secure-only uploads reject requests that would send a plaintext file body. Both remain opt-in to preserve Windows compatibility.
- Added bounded UDP work per IP and a maximum of 128 discovered peers. File offers are exposed only after their local history/file metadata writes succeed. Existing RSA/AES signatures, key pinning, replay defense and bounded transfer slots remain.
- Reused stream buffers replace per-chunk copies. File persistence happens on state changes, not every progress update. These are implementation improvements, not a measured claim about Wi-Fi throughput.

Remaining limits: IPMsg AES-CTR file data lacks a cryptographic integrity tag; discovery/ACK fields can be spoofed on a hostile LAN; TOFU keys need external fingerprint verification; source offers cannot resume across process death. Camera controls and external viewer/folder support depend on installed Android apps and document providers. Physical-phone camera recording, widgets across launchers, long Doze sessions and actual large Windows Wi-Fi transfers still need device acceptance.

## v0.3.0 review

- **P1: completed Windows downloads failed and were deleted.** The receiver required EOF after the advertised file bytes. In the Windows reference implementation (`src/mainwinfile.cpp`, `SendFileThread`, `complete_wait`), the sender waits for the receiver to close. This deadlock ended in Lantern's 20-second read timeout. The receiver now consumes exactly the advertised byte count, finalizes AES-CTR, flushes/closes the document and closes the socket. It does not read an extra byte. Empty files complete without reading the socket. Truncated transfers still fail and clean up partial documents.
- **P2: no unread or per-conversation controls.** Database v3 adds persisted read state, scoped to address plus peer user. Earlier history migrates as read; viewing a conversation in the foreground marks its new messages as read. The UI adds unread badges and a confirmation to clear one conversation. Replay records remain intact.
- **P2: ordinary text could route to Transfers.** Notification routing formerly compared the body to `File offer received`. It now uses a typed incoming event with its original peer identity and file-offer flag.
- Added the ZIP's useful workflow ideas while retaining Lantern's implementation and encryption: device search, transfer direction filters, percentage and received/expected byte diagnostics, network diagnostics, removable saved IPs and Android Back navigation.

The second reported error, `Connection ended before the advertised size`, indicates actual truncation rather than successful completion. It remains a failure; the new error includes exact byte counts. This release does not claim to repair Wi-Fi loss, sender shutdown, source-file changes or Android storage/provider failures. Ask Windows to resend a freshly offered file if retry fails.

Package ID and signing identity remain unchanged. Version code 3 / name 0.3.0, with in-place database v1/v2 → v3 migration. The original IPMsg logo and notices are retained. Sealed-message UI, broadcast-to-many and notification inline replies from the separate ZIP are not included in this update.

## Historical v0.2.0 review

The original build was a working interoperability prototype. Its happy-path tests were useful, but they did not justify production confidence: lifecycle failures, IP address reuse, restart behavior, and hostile LAN traffic were under-tested.

## Findings addressed

| Severity | v0.1.0 finding | v0.2.0 correction |
|---|---|---|
| P1 | Incoming messages were acknowledged before the database write. A crash or storage failure could lose a message after Windows believed it delivered. | Message content and replay ID commit in one SQLite transaction before acknowledgment. |
| P1 | Cached keys were indexed by IP without consistently checking the packet user/host. Unsigned encrypted messages from signing-capable peers were accepted. | Bind message, receipt, exit, and file-request handling to the announced identity; reject unsigned downgrades for signing-capable peers. Classic UDP control packets still cannot provide cryptographic authentication. |
| P1 | Packet IDs restarted from the current second. A fast process restart could reuse IDs and make peers discard legitimate messages. | Durably reserve blocks of IDs before sending; never reuse a reserved block after process death or clock rollback. |
| P1 | Histories were grouped only by IP. DHCP reuse could show an earlier device's conversation under a new device, and sending did not check the intended identity. | Persist peer user IDs, separate conversations by address and user, and check the selected user before sending. Earlier-version history remains readable and is not silently assigned to a new peer. |
| P2 | Replay suppression disappeared on restart, allowing a captured signed message to reappear. | Durable, bounded receipt ledger. Duplicate packets are acknowledged but do not create a second message. |
| P2 | Drafts were cleared before validation and the UI limited characters while the engine limited UTF-8 bytes. | Keep per-conversation drafts until queue acceptance; enforce the byte limit in the editor. |
| P2 | File-picker routing/save state used ordinary `remember`; rotation could lose the target or leave an orphan document. | Save pending transfer IDs, recipient identity, and draft with `rememberSaveable`; reject expired state safely. Sharing confirmation is intentionally dismissed on recreation and must be requested again. |
| P2 | An idle timeout could be extended indefinitely by trickling request bytes. Upload writes could stall permanently. | Total TCP handshake deadline, explicit packet-size/termination checks, and a stalled-upload watchdog. |
| P2 | Expired upload offers remained marked as awaiting acceptance. Failed downloads had no retry action. | Expiry updates transfer status; add retry from byte zero, improve partial-document cleanup, and provide Open after saving. |
| P2 | `NOLOG` messages were omitted from the conversation altogether. | Display them in bounded volatile memory without storing their bodies. Only receipt metadata is retained for replay defense. |
| P2 | Notifications replaced each other and opened a generic screen. | Separate notifications by sender address and route taps to the conversation or Transfers. |
| P3 | No history search, message copying, system dark theme, or clear original-icon attribution. | Add search, selectable/copyable messages, dark theme, readable system-bar icons, original IPMsg launcher/header artwork, a monochrome notification adaptation, and bundled attribution. |

## Compatibility and upgrade

- Package ID and debug signing identity are unchanged; version code increases to 2, version name to 0.2.0. Install over the previous APK to preserve data.
- Database version 1 upgrades in place to version 2. Previous messages remain available under Earlier version history. Start a new identified conversation from Nearby when replying to those devices.
- The classic IPMsg transport, port 2425, RSA/AES formats and Windows interoperability fixture remain unchanged.
- The exact original icon comes from the author's public source distribution. The BSD notice is bundled in the APK and source. Lantern remains an independent companion, not an official Windows IP Messenger release.

## Remaining limits

- IPMsg's classic AES-CTR file body has no integrity/authentication tag. This cannot be fixed unilaterally while retaining the Windows protocol. Compare file hashes for sensitive transfers.
- Discovery, plaintext and UDP acknowledgments can be spoofed by an attacker on the LAN. Matching user/host fields is not cryptographic authentication. First-contact key trust still needs external fingerprint verification.
- Replay protection is bounded to roughly 8,192 recent receipt IDs (up to 8,255 between pruning passes). Old replay IDs can eventually age out. Clearing message history retains this content-free security ledger.
- Transfers/offers remain session-only; there is no process-death resume or offline message queue. Retry requires the sender's offer to remain valid and may require a fresh offer on Windows.
- Background reception remains subject to Android and manufacturer battery policies. This update does not claim always-on delivery under Doze.
- Folder transfer, calls, IPv6 and Member Master remain outside this version. Very large transfers and extended physical-phone battery/Wi-Fi testing remain outstanding.
