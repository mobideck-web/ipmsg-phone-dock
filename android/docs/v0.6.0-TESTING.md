# IPMsg 0.6.0 release-candidate validation

November 5, 2026. Android 10+, application ID app.lantern.lan, version code 6. Physical-phone acceptance is explicitly pending at the user's request.

## Build and static checks

31 JVM tests passed: protocol/crypto 13, network safety 7, file transfer 5, packet rate limiting 2, HTTPS camera server 4. Android lint: zero errors and 67 warnings, including dependency/target-age, deprecated APIs and layout/resource advice. An initial incremental lint analysis crashed in the Kotlin analysis library while a test fixture was being added; a cleanly sequenced rerun passed without disabling lint.

Release shrinking is enabled. The candidate uses external private-key signing and Android v3 certificate rotation lineage from the original test key. No signing secrets, personal history, staged files or installed-app data are included in the source archive.

## Runtime checks

Twenty substantive Android runtime cases passed across focused runs on an Android 15 emulator using the unminified build of the same production sources:

- Eight engine/database cases: actual UDP/TCP, Keystore-backed signed messaging, acknowledgments/retries, duplicate suppression, ordinary/encrypted/empty/truncated/cancelled transfers, history migrations and durable file links.
- Five product cases: fingerprint approval across addresses, rejection of missing/changed keys and revocation, search beyond 2,000 messages with non-overlapping pages, review-only outbox staging, invalid share rejection and incomplete-destination cleanup.
- Five UI cases: first-device approval/cancellation, separate camera consent, drafts and search, unread/conversation controls, source-chat file actions and settings switch persistence. The preview PNG is a real screenshot of synthetic test messages.
- Two camera/storage cases: actual Camera2 frames, authenticated HTTPS recording requests, no recording before approval, decline/approve/stop, playable MP4, link revocation after leaving, pending download publication and separate duplicate filenames. The final camera/storage run passed in 75.497 seconds.

The debug-only signing guard in ProductTest returns without testing release signing and is excluded from the twenty-case count. Release evidence is reported separately below. Initial UI attempts encountered an emulator System UI ANR; the five UI cases passed after restarting that system component. A test-only external provider was rewritten in Java after its separate process could not load Kotlin runtime classes.

The first native TLS camera run exposed an Android Keystore RSA signing/padding incompatibility. The camera now uses a non-exportable Keystore P-256 ECDSA key, including authorization for the TLS stack's prehashed signature operation. Native TLS/recording tests passed after that correction. Windows IPMsg's own RSA messaging identity is unchanged.

Windows Chrome 156.0.8078.80 and Edge 156.0.4314.50 each rendered the authenticated HTTPS viewer, enabled its recording controls and requested a frame using an isolated headless test profile and a pin for the expected certificate public key. The Android endpoint fixtures also completed successfully (Chrome 47.62 seconds, Edge 43.732 seconds). These were emulator-loopback/ADB-forwarded checks against the unminified build, not physical Wi-Fi tests. The browser wrong-key/error-page automation timed out and is not counted as a passed certificate-substitution test. JVM TLS tests do reject untrusted certificates. Manual certificate inspection/site-specific exceptions, substitution handling and real-LAN browser setup remain pending.

Earlier v0.5 reports in docs/ are historical evidence and are not counted as this release's validation.

The exact corrected, shrunk release APK passed a framework-only probe: non-debuggable flags; original signing certificate present in the verified rotation lineage; retained identity and one persisted fixture message across an in-place update from the unminified 0.6 build; schema version 6; and an actual Camera2-backed HTTPS endpoint reached with certificate trust and HTTPS address verification. The probe returned PASS. The earlier 0.5 APK also accepted the first release-key candidate as an in-place update without uninstalling; history migrations were checked by the database cases above. Physical-phone upgrade acceptance remains pending.

The probe is test-APK-only, requires an explicitly approved loopback fixture and does not expose a remote activation interface in the delivered app. Build it with `:app:assembleDebugAndroidTest -PipmsgRunner=app.lantern.lan.ReleaseProbe`; test and target APK signatures must match. Normal behavior tests use the default AndroidJUnitRunner.

## Pending physical acceptance

No physical Android phone is connected. Check against Windows IP Messenger 5.9.1 on a real LAN before considering this a daily-use release:

- Discovery, Unicode, duplicate packets, address/key changes, offline recipients, Wi-Fi reconnection, screen-off reception and notification reply/read actions.
- Empty, duplicate-name, large, interrupted, cancelled, expired and multi-file transfers; low storage; revoked folder access; process death. Check that Saved appears only after the destination is complete.
- Edge/Chrome manual certificate inspection and site-specific exception, fingerprint mismatch, renewed certificates, expiry/revocation, denied and approved recording, playable real-camera recordings and leaving/locking/network-change cleanup.
- Upgrade preservation, large histories, large text, dark mode, TalkBack and OEM file/camera providers.
- Sustained throughput, memory and battery comparisons against v0.5. No improvement in Wi-Fi speed, battery or memory is claimed from build size or emulator tests.

## Known limits

Retries restart downloads from zero. Offers do not survive process death. Classic IPMsg encrypted files do not authenticate their contents. Custom providers can prevent immediate deletion or hide destination size; transfer byte counts are still checked. Android/OEM background policies may interrupt listening. A camera viewer can independently record its screen. The app's owner permission governs only IPMsg's own recorder. No live audio or remote storage access.
